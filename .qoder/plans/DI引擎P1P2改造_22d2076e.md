# DiContext 插件体系化改造

## 背景

当前 `DiContext` 链路与三套插件体系（数据源/分析引擎/同步引擎）脱节：
- `DiContext.Endpoint` 固定字段（host/port/username...）只能表达 JDBC，Kafka/MinIO 无法接入
- `SyncEndpointResolver` 中心硬编码字段名映射（user/username、database/schema），新增数据源要改平台核心代码
- `resolveAnalysisTarget` 被下沉到 `DatasetTask`，编排层直接依赖 `EngineService`（引擎知识泄漏）

业界模式（SeaTunnel/Airbyte/DataX）：config schema 插件自声明，平台透传不解析字段名，翻译归插件。

DataWorks 数据集成参照：所有来源/去处统一抽象为“数据源”（分析引擎如 AnalyticDB 不作特殊处理），同步任务 = Reader + Writer 任意组合，参数规范由插件自描述，新增数据源只加插件（N+M）。

核心抽象（导入/导出对称）：
- 分析引擎本质上也是一种数据源：DatasetTask（三方→分析引擎）与 ExportTask（分析引擎→三方）是同一件事的两个方向，任意 source×target 组合应可用
- 翻译① 平台配置 → 中性端点（config schema 知识）：统一归 connector 插件体系——source 和 target 都按 category 分派到 connector 插件；分析引擎与普通数据源的区别只在“配置来源”（Engine.config vs DataSource.config），不在翻译路径（ClickHouse connector 一份翻译同时服务两种场景）
- 翻译② 中性端点 → 引擎私有请求（引擎方言）：已在 DI 引擎插件（DiRequestBuilder），无争议

## Task 1：DiContext.Endpoint 泛型化

文件：`profile-engine/profile-engine-api/src/main/java/com/data/engine/api/DiContext.java`

Endpoint 删除固定连接字段（host/port/database/username/password/properties），改为：
```java
private String category;                  // 数据源类别：mysql / kafka / clickhouse ...
private Map<String, Object> config;       // 归一化后的连接配置（插件翻译产出，对平台不透明）
private String tableName;
private List<String> columns;
private String writeMode;                 // 仅 target：写入模式（平台级策略）
private Integer batchSize;                // 仅 target：批大小（平台级策略）
```

## Task 2：翻译器 SPI：统一归 connector 插件体系（source/target 对称）

1. 新建 `DiConfigTranslator` 接口，放 `profile-spi`（connector-api 与 engine-api 均已依赖，避免模块间新增依赖）：
```java
/** 同步配置翻译：把本插件管辖的原始 config 归一化为同步链路消费的连接配置 */
Map<String, Object> translate(Map<String, Object> rawConfig);
```
2. `ConnectorFactory` 新增可选能力（default 返回 null = 原样直通），source 与 target 共用：
```java
default DiConfigTranslator getDiConfigTranslator() { return null; }
```
3. JDBC 系 connector 插件（mysql / postgresql / clickhouse）提供共享归一化实现（放 `profile-connector-jdbc`）：`user→username`、`schema→database` 字段名收敛——字段名知识归属各自插件，N+M 复杂度；**ClickHouse connector 一份实现同时覆盖：分析引擎作目标 + CK 数据源作源/目标**
4. kafka / minio connector 暂不实现（直通），为非 JDBC 端点（导入源或导出去向）留好扩展位

## Task 3：SyncEndpointResolver 改造为分派器

文件：`profile-web/src/main/java/com/data/profile/web/engine/SyncEndpointResolver.java`

- 内部核心方法：`translate(category, configJson)`——按 category 取 `ConnectorFactory` 插件，有翻译器则翻译、无则直通；平台不认识任何字段名，导入/导出共用一条分派路径
- `resolveSource(DataSource, table, columns)`：便捷入口，从 `dataSource.getDatasourceType()`/`getConfig()` 取 category/config 后走核心分派（三方数据源作源：DatasetTask 现状；作目标：ExportTask 现状与未来）
- `resolveTarget(category, configJson, table, columns)`：便捷入口，走核心分派后附带平台级 `writeMode`/`batchSize`（分析引擎作目标：门面传入 engineType/config；三方数据源作目标：ExportTask 未来传入）
- 删除全部硬编码字段名映射（host/user/username/database/schema 的 getString/firstNonBlank 逻辑），删除未使用的 `DataSourceDTO` 导入

## Task 4：翻译②——各 DI 引擎插件的 DiRequestBuilder 消费中性端点

category → 引擎插件体系的映射、归一化字段 → 引擎参数摆放属引擎方言，归各 DI 引擎插件；不支持的组合（如 DataX + kafka 源）抛明确异常。

### 4a. DataX：适配泛型 Endpoint（改造现有）
文件：`profile-engine/.../profile-engine-datax/src/main/java/com/data/engine/plugin/datax/builder/DataXRequestBuilder.java`
- `buildJdbcSource(Endpoint)` 改为从 `endpoint.getConfig()` 按归一化后字段名读取（host/port/database/username/password/properties）
- jdbcUrl 拼接与 driverClass 映射的 switch 保留在 DataX 插件内（JDBC URL 属 DataX 方言，合理）
- 不支持的 category 抛明确异常："DataX 不支持 [category] 作为同步端点"

### 4b. SeaTunnel：新建 SeaTunnelRequestBuilder（补齐半成品链路）
文件：`profile-engine/.../profile-engine-seatunnel/` 新建 `SeaTunnelRequestBuilder`，并在 `SeaTunnelDiEngineFactory.getRequestBuilder()` 返回（消除当前返回 null 的地雷）
- 消费中性 Endpoint 生成 HOCON conf：
  - `env { job.name = jobId, parallelism = channel }`
  - `source { ... }`：category 映射 SeaTunnel 连接器（mysql/postgresql/clickhouse → `Jdbc`，kafka → `Kafka`），归一化字段 → SeaTunnel 参数名（url/user/password/table/column）
  - `sink { ... }`：clickhouse → `Clickhouse` sink（host/database/table/bulk_size=batchSize/writeMode），jdbc 系 → `Jdbc` sink
- conf 文本写入临时文件 → `ExecutorRequest.configPath`（P1 的 SeaTunnelDiEngineExecutor 已按 configFilePath 提交，无需再改）

## 收益与导入/导出对称性

- DataWorks 式抽象落地：所有端点（三方数据源/分析引擎）统一按 category 走 connector 插件翻译，平台只做分派与透传，不认识任何字段名；DI 引擎插件管方言转换（DataX/SeaTunnel 各自实现）
- **导入/导出对称**：`DatasetTask`（三方→分析引擎）与未来 `ExportTask`（分析引擎→三方）共用同一套 `DiContext`/resolver/门面契约，任意 source×target 组合可用；ExportTask 现有 P1 管道链路（EngineSource 流式读 + connector Executor 写）不动，DI 链路作为导出的可选通道零契约成本接入
- 新增数据源类型：只需在 connector 插件实现翻译器（或直通），平台与引擎插件零改动（N+M）；该数据源自动可用于导入源、导出去向任意方向
- 非 JDBC 同步源（Kafka/Hive）可表达：Endpoint 泛型化后无结构障碍
- 编排层不再依赖 `EngineService`，四层职责边界恢复
