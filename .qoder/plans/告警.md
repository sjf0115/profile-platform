# 任务监控告警功能

## 一、目标与范围

对标阿里云 DataWorks 的"任务级告警配置"：告警配置直接内嵌在任务上，事件驱动触发（任务实例执行结束按触发条件发送），复用现有 `profile-notification` 的 email 插件。

- 范围：事件驱动，不引入 Quartz 周期巡检。
- 通道：UI 展示 短信/邮件/电话/钉钉群机器人/WebHook 五项；**本期只真实现「邮件」**，其余四项前端展示为禁用（提示"敬请期待"），后端枚举预留、发送时跳过并记录。
- 前端：含完整前端（配置展示卡片 + 编辑对话框）。
- 不做"接收组"概念，接收人直接选「任务责任人」或「其他指定用户」。

### 数据模型（告警配置内嵌任务，对标 DolphinScheduler）

- `profile_meta_task` 加 3 列承载告警配置：`alert_condition`、`alert_channels`、`alert_receivers`（与任务 1:1、生命周期一致、删任务自然删配置，无需独立表与外键一致性维护）。
- `profile_meta_alert_history`：告警发送记录（每次触发一条，独立表）。
- 接收人条目化：`alert_receivers` 存 JSON 数组，每条 `{"type":..,"value":..}`，type 见 `AlertReceiverType` 枚举（OWNER/USER，预留 GROUP/ROLE），未来支持告警组零表结构改动。

### 触发流程

```
任务实例结束(TaskExecutionService.executeAsync)
  -> markSuccess / markFailed 之后
  -> AlertService.trigger(task, instance, status)
       0. 判断触发来源(instance.triggerMode): 仅 SCHEDULED(2)/API(3) 继续;
          MANUAL(1,手动执行)直接 return —— 用户在页面即时可见结果, 无需再发告警打扰
       1. 查 task 的告警配置; 无配置或未启用则直接 return
       2. 判断 alert_condition 是否命中当前 status
          (FAILURE 命中失败 / SUCCESS 命中成功 / FINISHED 成败都命中)
       3. 解析报警方式(alert_channels): 本期仅处理 email, 其余记录"通道未实现"跳过
       4. 解析接收人(alert_receivers JSON 条目, 按 type 分派):
            {type:owner} -> task.owner(userId) -> userService.getDetail -> user.email
            {type:user}  -> value(userId)      -> userService.getDetail -> user.email
            {type:group} -> 展开告警组成员(未来) -> 查 user.email
            去重、过滤空邮箱
       5. 从 SystemConfigService 读取 smtp 组配置，构建 NotificationSenderConfig
            + NotificationReceiverConfig({"to":"a@x.com,b@x.com","cc":""})
       6. NotificationManager.notify(message, {sender: {receiver}})
       7. 落 profile_meta_alert_history 记录
```

- 触发放在 `TaskExecutionService` 统一处理（而非各 Executor 的 onSuccess/onFailure），一处集成覆盖所有任务类型；手动/定时/API 三种触发都汇聚到 `executeAsync`，通过 `instance.triggerMode` 区分来源。
- **告警仅对无人值守场景生效**：仅 `TriggerMode.SCHEDULED`（定时调度）与 `API`（外部触发）发送，`MANUAL`（手动执行）跳过。
- 告警发送**不得影响任务主流程**：整个 `AlertService.trigger` 用 try/catch 包裹，异常仅记日志+落失败记录。

### 关键约束（复用 email 插件的既有契约）

- **EMailSender 构造器**通过 `NotificationSenderConfig.config`（JSON 字符串）解析配置，`JSONUtils.toMap` 后按 key 读取。**JSON key 必须严格为**：`serverHost`、`serverPort`、`sender`、`enableSmtpAuth`、`user`、`passwd`、`starttlsEnable`、`sslEnable`、`smtpSslTrust`。
- **SMTP 配置来源**：从 `SystemConfigService.getConfigByGroup("smtp")` 获取 `Map<String, String>`，key 恰好与上述 EMailSender 期望的 key 一致（因为前端通用配置页保存时用的 field 就是插件 Schema 定义的 field）。直接 `JSONUtils.toJsonString(smtpConfig)` 即可作为 `NotificationSenderConfig.config`。
- **message 格式**：`EMailSender.sendMails` 中 `wrapHtml` 会将非 HTML 文本自动包裹为 HTML 表格。如果 message 以 `<!` 开头则直接作为 HTML 发送。告警内容建议使用 HTML 格式，展示更清晰。
- **接收人配置**：`NotificationReceiverConfig.config` 为 `ReceiverConfig` 的 JSON：`{"to":"a@x.com,b@x.com","cc":""}`（to 逗号/分号分隔）。

DROP TABLE IF EXISTS `profile_meta_alert_history`;
CREATE TABLE IF NOT EXISTS `profile_meta_alert_history`(
    `id` BIGINT UNSIGNED AUTO_INCREMENT COMMENT '自增ID',
    `history_id` VARCHAR(40) NOT NULL COMMENT '告警记录ID',
    `task_id` VARCHAR(40) NOT NULL COMMENT '任务ID',
    `instance_id` VARCHAR(40) COMMENT '触发的任务实例ID',
    `alert_condition` VARCHAR(20) NOT NULL COMMENT '命中的触发条件',
    `alert_channel` VARCHAR(20) NOT NULL COMMENT '发送通道:email等',
    `receivers` VARCHAR(500) COMMENT '实际接收人(邮箱,逗号分隔)',
    `subject` VARCHAR(200) COMMENT '告警标题',
    `content` TEXT COMMENT '告警内容',
    `send_status` TINYINT NOT NULL DEFAULT 0 COMMENT '发送状态:0-失败,1-成功,2-跳过(通道未实现/无接收人)',
    `send_message` VARCHAR(500) COMMENT '发送结果说明',
    `creator` VARCHAR(100) NOT NULL COMMENT '创建者',
    `modifier` VARCHAR(100) NOT NULL COMMENT '修改者',
    `gmt_create` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `gmt_modified` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (`id`),
    UNIQUE (`history_id`),
    KEY `idx_task` (`task_id`),
    KEY `idx_instance` (`instance_id`)

## 五、后端实现（profile-web）

### 枚举（profile-common/.../enums/）

- `AlertCondition`：`FAILURE("failure","执行失败")`、`SUCCESS("success","执行成功")`、`FINISHED("finished","执行完成")`；含 `isMatch(InstanceStatus)`。
- `AlertChannel`：`SMS("sms","短信")`、`EMAIL("email","邮件")`、`PHONE("phone","电话")`、`DINGTALK("dingtalk","钉钉群机器人")`、`WEBHOOK("webhook","WebHook")`；含 `isImplemented()`（仅 EMAIL 返回 true）。
- `AlertReceiverType`：`OWNER("owner","任务责任人")`、`USER("user","指定用户")`，预留 `GROUP("group","告警组")`、`ROLE("role","角色")`；用于 `alert_receivers` 条目的 type，解析器按 type 分派取邮箱。

### Model（com.data.profile.web.model）

- `Task`（现有类）新增 3 字段：`alertCondition`（String）、`alertChannels`（String）、`alertReceivers`（String）。
- `AlertReceiver`（轻量 POJO，用于 alert_receivers JSON 序列化）：`type`（String）、`value`（String）。
- `AlertHistory`：id, historyId, taskId, instanceId, alertCondition, alertChannel, receivers, subject, content, sendStatus, sendMessage, creator, modifier, gmtCreate, gmtModified。

### DAO + XML

- **TaskMapper.xml 补 3 列**：在 `Base_Column_List`、`insertSelective`、`updateByTaskIdSelective` 中追加 `alert_condition`/`alert_channels`/`alert_receivers`。
- **AlertHistoryMapper**（新增）：`insertSelective`、`selectByTaskId`、`selectByParams`。
- 对应 `AlertHistoryMapper.xml`（BaseResultMap + Base_Column_List + insertSelective trim 写法，与 TaskMapper.xml 一致）。

### Service

- **TaskService 追加告警配置读写**：
  - `saveAlertConfig(String taskId, Task alertPart)`：将 3 个告警字段通过 `updateByTaskIdSelective` 写入 task。
  - `getAlertConfig(String taskId)`：从 task 详情取 3 个告警字段返回。

- **AlertService（核心触发）**：注入 `SystemConfigService`、`NotificationManager`、`TaskService`、`UserService`、`AlertHistoryMapper`。
  - `void trigger(Task task, TaskInstance instance, InstanceStatus status)`：整体 try/catch，实现第二节触发流程。**首步先判断 `instance.getTriggerMode()`，MANUAL(1) 直接 return。**
  - `buildAlertContent(Task task, TaskInstance instance, InstanceStatus status)`：构建 HTML 格式告警内容（任务名称、任务ID、执行状态、触发条件、开始/结束时间、失败原因等）。
  - `resolveReceivers(Task task)`：解析 `alertReceivers` JSON → 按 `AlertReceiverType` 分派（owner→task.owner；user→value；group→展开成员[未来]）→ userId 集合 → `userService.getDetail` 取 email → 去重去空。

### 触发集成（修改 TaskExecutionService.executeAsync）

现有 `executeAsync` 方法结构：
```java
// 成功分支
executor.execute(context);
taskInstanceService.markSuccess(instanceId, "执行成功");
executor.onSuccess(context);

// 失败分支
taskInstanceService.markFailed(instanceId, e.getMessage());
executor.onFailure(context, e);
```

改造点：
- 注入 `@Resource AlertService alertService;`
- 成功分支 `markSuccess` 后追加：
  ```java
  try { alertService.trigger(task, instance, InstanceStatus.SUCCESS); }
  catch (Exception ex) { log.warn("告警触发异常(不影响主流程)", ex); }
  ```
- 失败分支 `onFailure` 后追加：
  ```java
  try { alertService.trigger(task, instance, InstanceStatus.FAILED); }
  catch (Exception ex) { log.warn("告警触发异常(不影响主流程)", ex); }
  ```

## 八、风险与约束

- **告警不阻断主流程**：`AlertService.trigger` 全程 try/catch，异常仅记录，不向上抛。
- **SMTP key 严格对齐**：`NotificationSenderConfig.config` 的 JSON key 必须是 `EMailSender` 构造器读取的 9 个（serverHost/serverPort/sender/enableSmtpAuth/user/passwd/starttlsEnable/sslEnable/smtpSslTrust）。从 `SystemConfigService.getConfigByGroup("smtp")` 获取的 map key 即为这些 field（由邮件插件 Schema 定义），直接 `JSONUtils.toJsonString` 即可。
- **SPI 依赖 classpath**：email 插件 jar 已被 profile-web 打包依赖（前序工作已完成），`PluginLoader` 可正常加载 `email` 插件类型。
- **接收人无邮箱**：owner/指定用户 email 为空时跳过并在记录中标注 send_status=2。
- **通道未实现**：勾选 email 以外通道时后端跳过并落"通道未实现"记录，前端已禁用规避。
- **接收人 JSON 健壮性**：`alert_receivers` 解析失败或为空视为无接收人，跳过发送并落 send_status=2；未知 type 忽略。
- **告警适用范围**：仅 `TriggerMode.SCHEDULED`（定时调度）与 `API`（外部触发）发告警，`MANUAL`（手动执行）跳过——手动执行用户在页面即时可见结果，无需打扰。
