# 画像平台权限体系设计

## 一、设计目标与参考

对标 DataWorks 权限模型 + 神策用户画像平台，结合本平台单工作空间现状，构建三层权限：

1. **功能权限（RBAC）**：控制「谁能看哪些菜单/按钮、能调哪些 API」——用户 → 角色 → 权限点。
2. **数据权限（ACL）**：控制「谁能读/写/导出/管哪些具体资源」——默认归属制（owner/creator），叠加资源级显式授权。
3. **审批流（仅数据权限）**：非本人资源通过「申请 → owner/管理员审批 → 授权落地」获取访问权。角色/功能权限不走申请，由管理员在创建/编辑用户时直接分配。

**复用现状**：JWT 认证链、`UserContextHolder`、`Role/UserRole`、各资源已有的 `owner/creator` 字段、`ModelType.PERMISSION("19")`。不引入 `workspace_id`（保持单空间精简 RBAC）。

## 二、权限模型总览

```
用户(User) --N:N--> 角色(Role) --N:N--> 权限点(Permission: 菜单/按钮/API)
                                    ↓
资源(dataset/label/group/...) --ACL授权(ResourceGrant)--> 用户 或 角色 (READ/WRITE/EXPORT/MANAGE 可组合)
                                    ↑
                        申请单(AuthApply) → 审批 → 写入 ResourceGrant
```

- **功能权限判定**：`用户角色的权限码集合` 是否包含目标权限码。
- **数据权限判定顺序**：`超级管理员` → `owner==当前用户 或 creator==当前用户`(视为全动作) → `ResourceGrant 命中(用户/角色, action)` → `系统内置资源(source_type=1)默认全员 READ` → 否则拒绝。
- **数据权限动作为可组合位**（对标 DataWorks Select/Update/Download 并列勾选）：`READ`(查看/被引用)、`WRITE`(编辑)、`EXPORT`(导出/投递/下载)、`MANAGE`(删除/转移owner/授权他人)。判定时 **MANAGE 隐含 R/W/E**（拥有 MANAGE 即视为拥有全部动作，`DataAuthService` 内实现），授权时无需重复勾选；可只授 READ 不授 EXPORT。
- **灰度开关**：新增配置 `profile.permission.enabled`(默认 false)。为 false 时功能/数据权限切面直接放行，避免存量用户无角色被全拦；初始化好角色与授权后再置 true。

## 六、权限清单与角色规划

### 6.0 业界参考与设计原则（对标神策）
- 功能权限**不按列表/详情拆分**——`view` 覆盖列表+详情；「能否看到某资源详情」由**数据权限**决定；详情页敏感字段由 `viewSensitive` 脱敏控制。
- 神策「管理自己创建的 vs 管理全部」对应本方案 `owner/creator 命中=管自己` 与 `管理员/授权=管全部`。

### 6.1 动作集

## 八、风险与约束
- 列表数据过滤须覆盖所有资源查询入口，统一收敛到 Service 层，避免绕过。
- `owner/creator` 存的是 userId，判定统一以 userId 为准。
- 临时授权 `expire_time` 查询时判过期（可加定时清理）。
- 初始 admin(100000) 必须绑定超级管理员，避免升级后自锁。
- `resource_type` 统一用 `ModelType` 码字符串；注意 group_analysis 无码，需先补 `GROUP_ANALYSIS("22")`。
- **性能**：权限加载勿在拦截器逐条查库（现已每请求查一次 `getDetail`），合并为一次 join + Caffeine 缓存（TTL 30~60s）。
- **灰度**：开启校验前须给存量用户批量赋默认角色，或用 `profile.permission.enabled` 开关平滑上线。
- **⚠️ source_type=1 全员 READ 安全边界**：内置资源默认全员可读，需确保 `DataAuthService` 判定时仅在「功能权限通过」后才放行 READ，否则未登录/无角色用户也能通过 DataAuth 切面读到数据。
- **⚠️ 删角色级联**：`RoleService.delete` 必须同时清理 `user_role` + `role_permission`，当前仅清 user_role（P0-2 已纳入修复）。

## 九、技术栈与编码约定（自包含执行前提）

> 换机执行时按此节对齐环境与写法，无需再翻现有代码。

### 9.1 后端（profile-web，Java 8 + Spring Boot 2.7.5 + MyBatis）
- 分层：`controller` → `service`(接口+`impl`) → `dao`(Mapper 接口) + `resources/mapper/*.xml`；model 放 `web/model`。
- 分层对象规范：Param（查询入参）、Request（写入入参）、VO（返回视图）、Model/DO（数据库实体）；Controller 只做 DTO↔VO 转换，Service 返回 DTO 或 Model。
- Converter 规范：MapStruct + BaseConverter + xxx2yyy 命名（dto2vo/param2do/request2do/do2vo），禁止 BeanUtils。
- 统一返回体 `com.data.profile.web.vo.Response`（**非 common 包**）：`Response.success(data)` / `Response.error(msg, ResponseCode)`，HTTP 200，业务码在 body `code`(成功 200)。
- 业务 ID：`IDGenerator.generateId(ModelType.XXX)`。⚠️ `ModelType` 现只到 `APPLICATION("21")` 且**无 group_analysis 码**，需新增：`GROUP_ANALYSIS("22")`、`GRANT("23")`、`AUTH_APPLY("24")`；权限点用现有 `PERMISSION("19")`。
- 当前用户：`UserContextHolder.currentUserId()` 取 userId（内部 `getUserContext().getUser()`）；写库 `creator/modifier` 填 userId。
- 时间字段 `gmt_create/gmt_modified` 由 DB 默认值维护，无需手填。
- 权限校验走 AOP 切面（参考 `aspect/ControllerExceptionAspect`），不改拦截器路径匹配。
- MyBatis 字段映射：DB 下划线 ↔ Java 驼峰（已开启 `map-underscore-to-camel-case`）；xml 用 `#{}` 占位，禁止拼接。

### 9.2 前端（profile-ui，Vue3 `<script setup>` + TS + Element Plus 2.13 + Pinia 3 + vue-router）
- 请求：`@/utils/request`（axios 实例，`baseURL=/api`，自动附 `Authorization: Bearer <token>`，响应码非 200/0 弹 `ElMessage.error`，401 清 token 跳登录）。
- Token：`@/utils/auth` 的 `getToken/removeToken`（localStorage）。
- 返回体类型：`@/types` 的 `ApiResponse<T>`（`{ code, message, data }`）。
- API 层：每模块一个 `src/api/xxx.ts`，导出 `xxxApi` 对象 + `interface`，方法用 `request.get/post/put/delete<ApiResponse<T>>`。字段名用**下划线**与后端一致（如 `role_name`）。
- 图标：`@element-plus/icons-vue`。反馈：`ElMessage`/`ElMessageBox`。
- 样式：`<style scoped lang="scss">`，页面根 class + `padding:20px`。
