# 数据资产血缘关系与查询执行计划

## 一、定位与业界依据（不过度设计 + 符合流行方案）

对标品类为增长分析/画像/CDP 产品（神策、字节 DataFinder、阿里 Quick Audience），而非数仓治理平台（DataWorks/Atlas）。调研结论：

- 神策：固定元数据层级 + 显式引用建模（虚拟属性显式"选择可用事件"）+ 删除依赖约束（"已上报数据的元事件不支持删除"、"删除元事件，引用它创建的资源也会不可用"）。无独立血缘大图。
- 字节 DataFinder / 阿里 Quick Audience：固定层级元数据模型，核心为资产管理与依赖，无血缘可视化大图。

由此定调：
- 核心能力 = 引用完整性 / 删除保护 / 依赖影响提示（雪中送炭，第一优先级）。
- 增值能力 = 轻量血缘上下游查询 + 可视化（锦上添花，不做字段级、不做图数据库）。
- 底座 = 统一血缘关系表(SSOT) + parse once 采集（复用现有解析），采集触发用 Service 事务内同步调用，明确不引入 Kafka/MQ/进程内事件/图库。
- 一致性 = 血缘维护并入业务本地事务，强一致原子提交（单库单体的优势，Atlas/DataLeap 跨进程只能最终一致，我们能做强一致）。
- 兜底 = 全量重建，定位为「首次初始化存量数据 + 灾难恢复」，不承担日常一致性职责。

## 二、资产关系模型（基于真实代码核验）

节点类型（8 类）：datasource / dataset / label / event / group / analysis / export / application。

引用边（downstream 引用方 -> upstream 被依赖方）及数据来源：

| 引用边(下游->上游) | 数据来源 | 采集方式 | 复用点 |
|---|---|---|---|
| dataset -> datasource | `dataset.datasource_id` | 直读字段 | - |
| label -> dataset | `dataset_field.related_id`(=labelId) 反查 `dataset_id` | 反查(仅 sourceType=2 绑定) | `datasetFieldService.getDetailByRelatedId` |
| event -> dataset | `event.dataset_id` | 直读字段 | - |
| group -> label / group | `group.group_rule`(JSON) 内 `RuleFilter.type=1/2` 的 `id` | 遍历规则树 | 抽取 `GroupService.collectMetadata` 逻辑 |
| analysis -> group / label | `group_analysis.group_id` + `compare_group_ids`/`label_ids`(JSON数组) | 直读+解析JSON数组 | `GroupAnalysisService.parseJsonArray` |
| export -> group | `export.export_config`(JSON).`group_id` | 解析JSON | `ExportTask.parseExportConfig` |
| export -> application / datasource | `export_config`.`application_id`(mode=2) / `datasource_id`(mode=1) | 解析JSON | 同上 |

方向语义：upstream=被依赖方（数据来源），downstream=引用方（消费者）。删除保护 = 删 X 前查"谁把 X 当 upstream"（一跳）；血缘 = 多跳遍历。

## 五、后端实现

### 5.1 枚举（新增 `profile-web/.../enums/`）
- `AssetType`：节点类型。值用小写字符串（前端友好）：DATASOURCE/DATASET/LABEL/EVENT/GROUP/ANALYSIS/EXPORT/APPLICATION，含 code+name。
- `RelationType`：关系类型（对应 `relation_type` 列），code+**动词式**中文名映射（保证拼装语句通顺）：`derive`→派生自、`reference`→引用、`consume`→消费、`export`→投递自。提供 `getNameByCode(String)`，无匹配回退原始 code。
- **边类型表述**（如“群组引用标签”“群组引用群组”“标签引用数据集”）：由 `AssetType.name(downstream_type) + RelationType.name(relation_type) + AssetType.name(upstream_type)` 拼装，不落库（可推导，新增类型/改名零维护）；带实例名的整条描述见 5.8。若需按边类型统计，直接对 `(downstream_type, relation_type, upstream_type)` 三列 GROUP BY。
- （可选）`RelationPattern`：合法边模式白名单，枚举 2.2 表的 `(downstream_type, relation_type, upstream_type)` 组合，供 `LineageExtractor` 产出边时做合法性校验，拦截意外/非法边（非落库字段，为校验常量集）。

### 5.2 实体与 DAO（新增）
- `model/LineageEdge.java`：对齐 profile_meta_lineage 列。
- `dao/LineageEdgeMapper.java`(`@Mapper`)：
  - `int batchInsert(@Param("list") List<LineageEdge> list);`
  - `int deleteByDownstream(@Param("type") String t, @Param("id") String id);`（重写下游出边用）
  - `int deleteByNode(@Param("type") String t, @Param("id") String id);`（删节点全部出入边）
  - `List<LineageEdge> selectByUpstream(@Param("type") String t, @Param("id") String id);`（删除保护/影响分析一跳）
  - `List<LineageEdge> selectByDownstream(@Param("type") String t, @Param("id") String id);`（血缘上溯一跳）
  - `List<LineageEdge> selectUpstreamEdgesBatch(@Param("nodes") List<NodeRef> nodes);`（getGraph 逐层 BFS 批量查上游边；入参为本层 (type,id) 列表，xml 用 `<foreach>` 按 type 分组拼 `WHERE downstream_type = ? AND downstream_id IN (...)` 再用 OR 连接，避免元组 IN 优化器不友好）
  - `List<LineageEdge> selectDownstreamEdgesBatch(@Param("nodes") List<NodeRef> nodes);`（同上，批量查下游边，按 `(upstream_type,upstream_id)` 组合）
  - `NodeRef` 为轻量 DTO（type+id），仅作批量查询入参载体。
  - `int deleteAll();`
- `resources/mybatis/mapper/LineageEdgeMapper.xml`：BaseResultMap + 上述语句（参照 GroupMapper.xml 风格）。

### 5.3 血缘抽取器（parse once，新增，复用现有解析）
`service/LineageExtractor` 接口：`String assetType(); List<LineageEdge> extractUpstreams(String assetId);`（返回该资产依赖的上游边）。6 个实现：
- `DatasetLineageExtractor`：读 datasource_id（trivial）。
- `LabelLineageExtractor`：`datasetFieldService.getDetailByRelatedId(labelId)` -> dataset（复用现有）。
- `EventLineageExtractor`：读 dataset_id（trivial）。
- `GroupLineageExtractor`：遍历 `group_rule` 的 RuleExpression 收集 type=1 label / type=2 group。抽取 `GroupService.collectMetadata` 的遍历逻辑为公共工具，业务圈选与引用采集共用（消除双份 JSON 解析）。
- `AnalysisLineageExtractor`：group_id + compareGroupIds + labelIds（复用 parseJsonArray）。
- `ExportLineageExtractor`：ObjectMapper 解析 ExportConfig -> group / application(mode=2) / datasource(mode=1)（复用 parseExportConfig）。

### 5.4 血缘服务（唯一核心类 `LineageService`，读写合一）
`service/LineageService.java`，承载血缘关系的全部读写与治理能力（将原读/写两个 Service 合并为一个）：
- 写侧：
  - `void refreshLineage(String assetType, String assetId)`：调对应 Extractor 得上游边，`deleteByDownstream` 后 `batchInsert`（幂等，update 天然覆盖）。
  - `void removeLineage(String assetType, String assetId)`：`deleteByNode`。
- 一跳查询（删除保护/影响提示）：
  - `List<LineageEdge> findDependents(String assetType, String assetId)`：`selectByUpstream`。
  - `void checkDeletable(String assetType, String assetId)`：内部调 findDependents，有下游则抛业务异常（删除保护，见 5.6）。
- 多跳查询（血缘图/影响分析，见 5.8）：
  - `LineageGraphVO getGraph(String nodeType, String nodeId, String direction, int depth)`。
  - `List<ImpactVO> getImpact(String nodeType, String nodeId)`。
- 全量重建（见 5.7）：`int rebuildAll()`。

> 说明：写侧(强一致、事务)与读侧(多跳遍历、聚合)内职责不同，但按用户要求收敛为单一类；`LineageExtractor`(6个解析实现)作为 `LineageService` 依赖的解析组件保留。

### 5.5 采集触发（设在事务级业务方法，按节点维度整体重算）
触发点一律放在带 `@Transactional` 的业务 Service 方法内，**不下沉到 DAO 级方法（如 `datasetFieldService.save`）**。原因：`datasetFieldService.save` 是单条 upsert、无 `@Transactional`、且被 Controller/引擎多处复用；label↔dataset 边由 `dataset_field.related_id` 定义，其「删/换绑」路径（`LabelService.delete` 解绑走 `deleteByDatasetIdAndFieldName`、`DatasetService.updateDataset` 先 `deleteByDatasetId` 全删后重插、`DatasetService.delete` 删字段）都不经过 `save`——只埋 `save` 会漏采漏删、残留脏边，删除保护随之失效。
- 语义：create/update 后调 `lineageService.refreshLineage(type,id)`——按该节点维度**先 `deleteByDownstream` 删其全部上游边再 `batchInsert` 重建**，天然兼容「先删后插」式更新，不重复不残留；delete 前做删除保护校验、删除后调 `lineageService.removeLineage(type,id)`。
- 覆盖粒度原则（关键，修正 review #2）：`refreshLineage(X)` 按 `deleteByDownstream(X)` **只重建「以 X 为 downstream 的边」**。若某业务操作改变的是「以另一节点 Y 为 downstream 的边」，必须显式对受影响的 Y 逐个 `refreshLineage(Y)`，不能只刷新触发实体自身。本模型中唯一的跨实体反向影响是 label→dataset（downstream=label，却可被数据集侧操作改动），需专门处理（见下）。
- 触发落点（均为带 `@Transactional` 的业务方法）：
  - **前置依赖**：以下 Service 当前缺少 `@Transactional`，须在 P0 阶段补充：
    - `EventService`：save/create/update/delete 均无事务注解，须加 `@Transactional`
    - `GroupAnalysisService`：saveAnalysis/deleteAnalysis 无事务注解（已 import 但未使用），须加 `@Transactional`
    - `ExportService.delete`：仅 save 有事务，delete 无，须补 `@Transactional`
  - `DatasetService.save`（create/update 公共入口）→ ① `refreshLineage(dataset)` 维护 dataset→datasource 边（downstream=dataset）；② 因数据集侧「字段关联标签」改写 `dataset_field.related_id` 影响的是 downstream=label 的边，须取**受影响 label 集合**（旧 related_id ∪ 新 related_id；因 `updateDataset` 先 `deleteByDatasetId` 全删，必须在变更前先查旧值）逐个 `refreshLineage(label)`。伪代码：
    ```
    if (update):
      oldLabelIds = datasetFieldService.getByDatasetId(datasetId).stream()
                    .filter(f -> f.getRelatedId() != null)
                    .map(DatasetField::getRelatedId).collect(toSet())  // 必须在 deleteByDatasetId 之前
      updateDataset(...)  // 全删 + 重插字段
      newLabelIds = fields.stream().filter(f -> f.getRelatedId() != null)
                    .map(DatasetField::getRelatedId).collect(toSet())
      for (labelId in oldLabelIds ∪ newLabelIds): refreshLineage("label", labelId)
      refreshLineage("dataset", datasetId)
    else:
      createDataset(...)
      refreshLineage("dataset", datasetId)
      for (labelId in new fields' relatedId): refreshLineage("label", labelId)
    ```
    `DatasetService.delete` → 删除保护校验 + `removeLineage(dataset)` + 对其字段关联的各 label `refreshLineage(label)`（上游 dataset 消失后其 label→dataset 边被清除）。
  - `LabelService.save`（绑定/换绑 datasetField 分支）→ `refreshLineage(label)`；`LabelService.delete`（解绑 + 删标签）→ 校验 + `removeLineage(label)`。覆盖标签侧「绑定数据集字段」产生的 label↔dataset 边。
  - `EventService`、`GroupService`、`GroupAnalysisService`、`ExportService` 的 create/update/delete 同理。
- label↔dataset 双向绑定收口（对应 review #1）：标签侧 `LabelService.save`、数据集侧 `DatasetService.save` 两个入口最终都改写 `dataset_field.related_id`，但收口点应是这两个**事务级业务方法**、而非其共同调用的 `datasetFieldService.save`；因 label→dataset 边 downstream=label，两入口均需在各自事务方法内对该边的 downstream（label）执行 `refreshLineage(label)`（数据集侧对受影响 label 集合逐个刷新，见上），确保双向的增/改/删/解绑全覆盖。
- 明确不引入 Kafka/MQ/Spring 事件。
- 原子性（关键）：业务 Service 方法标 `@Transactional`；`refreshLineage/removeLineage` 内部 Mapper 走默认 `Propagation.REQUIRED`，自动加入调用方事务、共用同一数据库连接。业务写与血缘维护要么同时提交、要么同时回滚，血缘表永不与业务数据劈叉。
- 严禁 try/catch 吞掉 refreshLineage/removeLineage 异常（否则破坏原子性）；异常必须向上抛出触发整体回滚。
- 因写时强一致，血缘表在任意时刻均为最新，删除保护校验读到的即最新状态。

### 5.6 删除保护（第一优先级核心，对标神策）
`LineageService.checkDeletable()`：各资产删除入口先调它（内部 `findDependents`），若存在有效下游则抛业务异常，Controller 返回 `Response.error("该资产被 N 个下游引用，无法删除：{清单}", ResponseCode.ERROR)`。
- 策略：默认 RESTRICT（拒绝删除并列出下游）。
- 落点：GroupService.delete、LabelService 删除、DatasetService.delete、EventService 删除、ExportService 删除、GroupAnalysis 删除。
- 事务与并发（关键，确保删除时血缘最新）：删除全流程置于同一 `@Transactional` 内——① `SELECT ... FOR UPDATE` 锁定被删资产业务行 → ② `findDependents` 一跳查下游 → ③ 有下游抛异常回滚；无则删业务数据 + `removeLineage` 引用边 → 提交。
- 防 write skew（A 删 label X 与 B 新建引用 X 的 group 并发）：引用方(group/export...)保存时在事务内校验其上游资产存在；删除方对资产行加锁。二者形成锁竞争，杜绝「X 被删但 group 仍引用 X」的幽灵引用。本项目并发低，此基本防护足够，不做过度设计。

### 5.7 全量重建（首次初始化 + 灾难恢复，非日常一致性手段）
`LineageService.rebuildAll()`：`deleteAll()` 后遍历 dataset/label/event/group/analysis/export 逐个 `refreshLineage`（自身包在事务内）。定位明确为：① 上线时初始化存量数据；② 极端异常/人工订正后的灾难恢复。由于 5.5 写时强一致，日常无需依赖它保证一致性。仅提供手动触发接口，不做定时对账（低并发 + 写时强一致下无必要，避免过度设计）。

### 5.8 血缘查询（`LineageService` 多跳方法，增值）
均为 5.4 `LineageService` 的方法：
- `LineageGraphVO getGraph(String nodeType, String nodeId, String direction, int depth)`：基于 profile_meta_lineage 做**逐层 BFS**（direction=upstream/downstream/both，depth 默认3、上限10，visited 去重防环）：每层把本层全部待扩展节点收集为 (type,id) 列表，调 `selectUpstreamEdgesBatch/selectDownstreamEdgesBatch` **一次批量取边**（both 则两向各一次）得下一层节点——边查询次数由 O(节点数) 降为 O(depth×方向数)，杜绝逐点 N+1。遍历结束后收集全部节点按 type 分组，每 type 一次 IN 查询回填名称（各实体 Mapper 提供/新增 `selectNamesByIds`），组装 `{nodes:[{id,type,name}], edges:[{source,target,relation,relationName}]}`（`relationName` 由 RelationType 枚举按 relation 映射，非落库）。
- `List<ImpactVO> getImpact(String nodeType, String nodeId)`：复用同一逐层批量 BFS（direction=downstream、depth 取上限，visited 防环），返回受影响下游清单。
- 关系描述（如“群组_双11 引用 标签_近30天活跃”）由 `下游名 + relationName + 上游名` 实时拼接，不落库（同 relationName，避免资产改名后描述过时）；手动登记的自定义说明用 `remark` 字段。

### 5.9 Controller（新增 `controller/LineageController.java`）
`@RestController @RequestMapping("/lineage")`：

### 6.2 API 模块（新增 `src/api/lineage.ts`）
```ts

export interface LineageEdge { source: string; target: string; relation: string }
```

## 八、风险与约束

- 环状引用：group->group、组合人群等可能成环，BFS 必须 visited 去重 + depth 上限防死循环；删除保护一跳无环问题。
- 历史数据：上线先执行一次 `/lineage/rebuild` 初始化存量引用，否则删除保护与血缘均为空。
- parse once：GroupLineageExtractor 必须抽取复用现有 `collectMetadata` 遍历逻辑，严禁另写第二套 group_rule 解析，防止与圈选逻辑漂移。
- 采集与事务（强一致）：refreshLineage/removeLineage 并入业务 `@Transactional`，`Propagation.REQUIRED` 共用连接；任一步失败整体回滚，引用表与业务数据强一致。禁止吞异常。
- 删除并发：删除流程事务内 `SELECT ... FOR UPDATE` 锁定被删资产行 + 一跳查下游；引用方保存时校验上游存在，防 write skew 幽灵引用。
- 明确不做（避免过度设计）：不引入 Kafka/MQ/图数据库/Spring 事件总线；不做字段级血缘；不重构 group_rule/export_config 存储结构（规则树保持嵌套，仅新增引用投影）。
- 与权限体系计划相互独立；若后续接入权限，血缘/删除接口按已有资源可见性(label:view/group:view)过滤。
